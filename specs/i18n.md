# Translation (English and Brazilian Portuguese)

## Scope
The whole UI in English (default) and Brazilian Portuguese, with the locale in the URL, a language switch on the profile page and the AI summary in the viewer's language. Plan: `plans/03-product-reviews/i18n.md`.

## Context
Until now every screen was English, with copy collected in `src/i18n/dictionaries/en.ts` and read through a placeholder `t()`. Most users are in Brazil and the catalog comes from Amazon Brazil, so the UI needs Portuguese. Pages use Cache Components (static shell + streamed content), so the language cannot come from a cookie read in the root layout without making every page dynamic: it lives in the URL instead, as in the Next.js internationalization guide.

## Functional requirements
1. Locales: `en` (default) and `pt-BR`. Every page lives under a locale segment: `/en/home`, `/pt-BR/home`, `/pt-BR/products/<id>`; routes are in `src/app/[lang]/`
2. `<html lang>` is the locale of the URL; each page is prerendered per locale (`generateStaticParams` in the root layout)
3. URLs without a locale (old links, bookmarks, `/`) are redirected by `src/proxy.ts`, keeping the query string, to the locale chosen in this order:
    1. the `prs_locale` cookie (set when a signed-in user picks a language and at sign-in from the account)
    2. the browser's `Accept-Language` (`pt`, `pt-BR`, `pt-PT` → `pt-BR`; `en-*` → `en`; by `q` weight)
    3. `en`
4. The proxy never touches `/api/**`, `/_next/**`, static files (any path with a file extension) or BotID's challenge path
5. Any `/<locale>/...` URL without a page shows the localized 404 (`src/app/[lang]/[...rest]` → `[lang]/not-found.tsx`)
6. Dictionaries `src/i18n/dictionaries/en.ts` and `pt-BR.ts`; `pt-BR` is typed with the English keys, so a missing or extra key is a type error
7. Server Components read the locale from the `[lang]` root param (`getLocale()` / `getT()` in `src/i18n/server.ts`, `next/root-params`); client components use `useT()` / `useLocale()` from `<I18nProvider>` (`src/i18n/client.tsx`), which gets only the client message prefixes (`src/i18n/client-messages.ts`)
8. All UI copy is translated: pages, headers, catalog lists, pagination, product cards, forms, validation messages, toasts, empty and error states, the disclaimer, the 404 pages and page titles. Terminology in Portuguese: "avaliação" for both review and feedback, "avaliar" as the verb
9. Never translated: product titles (from Amazon), the reviews people write, the product name "Product Review System"
10. Formatting: dates with date-fns `enUS` / `ptBR` ("Member since October 2026" / "Membro desde outubro de 2026", relative dates "há 3 dias"), numbers with `Intl` ("1,234" / "1.234", averages "4.3" / "4,3"); prices are always BRL ("R$ 1.999,94") in both languages
11. Validation: the zod schemas return message keys (`validation.*`); the forms translate them, the REST API answers in English
12. Server errors: tRPC errors carry a message key (`data.messageKey`, `src/server/errors.ts`) that the UI translates; the error message itself stays English, so REST API responses do not change
13. Links: `localeHref(locale, path)` and helpers in `src/lib/routes.ts`, `LocalizedLink` for components rendered on both sides; no literal `/home`-style paths in pages, features or components (checked by a test)
14. Profile switch on `/me` (signed-in users only): a "Language" control with "English" and "Português" (each written in its own language). Changing it:
    1. calls tRPC `account.setLocale({ locale })` (protected), which saves `accounts.locale` and sets the `prs_locale` cookie (1 year)
    2. opens the same page in the new locale (full load, so `<html lang>` and the client messages change too)
15. Sign-in reads `accounts.locale`, sets `prs_locale` and sends the user to `/<locale>/home`; the language follows the account to other devices. Sign-out keeps the cookie
16. Visitors (landing, sign-in, sign-up) get the browser's language; there is no switch for them
17. AI summary in the viewer's language: the product page asks `getOrCreateSummary` for its locale (cache per product and locale). After a feedback, the background refresh runs for the author's locale and for every locale that already has a cached summary for that product
18. Migration `20261018220000_accounts_locale.sql`: `accounts.locale text not null default 'en' check (locale in ('en','pt-BR'))`

## Non-Functional requirements
- No new dependency (date-fns locales and `Intl` only)
- Pages keep their prerendered static shell per locale (no cookie or header read for the language in layouts)
- The browser only receives the messages client components use, never both dictionaries
- Summary cost stays tiny: at most one model call per product and language until its reviews grow 10%

## Must do
- Translate every existing English string, including copy that was hard-coded outside `en.ts`
- Keep old un-prefixed URLs working through redirects
- Update every E2E spec to run under `/en/...`

## Must not do
- Translate product titles, user reviews or REST API messages
- Read the language from a cookie in the root layout
- Add an i18n library

## Technologies (Stack)
- Next.js 16 `proxy.ts`, `[lang]` root segment, `next/root-params`, `generateStaticParams`
- React context for client messages
- date-fns (`enUS`, `ptBR`), `Intl.NumberFormat` / `Intl.DateTimeFormat`
- Supabase migration for `accounts.locale`

## Acceptance criteria
- A visitor with `Accept-Language: pt-BR` opening `/` lands on `/pt-BR` with the landing page in Portuguese and `<html lang="pt-BR">`
- A signed-in user switching to Português on `/en/me` lands on `/pt-BR/me` in Portuguese; `/home` then redirects to `/pt-BR/home` with Portuguese lists
- Signing out, clearing the device's cookies and signing in again lands on `/pt-BR/home` (account setting)
- Switching back to English works the same way
- Dates on `/me` show in Portuguese ("Membro desde …", "Publicada …"); product titles and review text stay as written
- `/api/**` answers exactly as before (English messages)
- Unit tests: dictionaries (same keys, no empty strings, same placeholders), `pickLocale`, the proxy, formatting, `account.setLocale`, the hard-coded routes scan, client message coverage; E2E `e2e/i18n.spec.ts` and every existing spec under `/en/...`

## Results
- Routes moved to `src/app/[lang]/`; `src/proxy.ts` redirects un-prefixed URLs
- `src/i18n/`: `locales.ts`, `dictionaries/{en,pt-BR,index}.ts`, `t.ts`, `server.ts`, `client.tsx`, `client-messages.ts`, `format.ts`, `price.ts`, `errors.ts`, `message.ts`
- tRPC `account.setLocale`; `auth.signIn` returns `locale`; `SessionUser.locale`
- Language switch on `/me` (`src/features/me/language-switch.tsx`)
